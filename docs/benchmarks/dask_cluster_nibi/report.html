SPIMquant --dask_cluster slurm: multi-node dask on Nibi

Run 2026-11-21 on Nibi, account rrg-akhanf_cpu, SPIMquant branch dask-slurm-cluster. Input: mind://scratch/spimquant-test/test_mind_1x/bids read straight from MIND (Arbutus), 1 subject, full resolution (11.7 GB per stain). Steps: n4_biasfield → gmmthresh → compute_filtered_regionprops, fieldfrac for 3 stains (Abeta, YoPro, CD31) at once, from the same registration outputs. Snakemake ran on the login node with --executor slurm. One run per configuration.

Findings

  • It works, and the results match. With --dask_cluster slurm, the three stains' jobs shared one dask cluster of 1, 2 or 3 nodes' worth of workers (2, 4 or 6 Slurm jobs of 96 cores) and gave the same thresholds and object counts as each other, and as the current local dask to within 0.03% and 0.6%.
  • One correctness bug had to be fixed first. On Nibi's /scratch (NFS), chunk files written by workers on one node were not all visible on another node right after the store had finished. zarrnii builds each pyramid level from the one it stored before, so one stain in three got levels of mostly zeros, which made gmmthresh fail. This happened only with several jobs on the cluster at once, and cannot happen within one node. Now, in cluster mode, every chunk is written (even empty ones) and each dask store waits until all of its chunk files can be opened on every node before returning. Two repeats of the test that had failed every time, plus all three benchmark runs, came out correct.
  • No speed-up for these steps: they are limited by reading from MIND, not by cores. Once workers were up, the three n4_biasfield jobs took 145–161 s with 1–3 nodes, against 195 s for the slowest stain with local dask (3 jobs × 128 cores). The workers averaged 5–11 cores busy out of 192–576. Adding nodes did not shorten the work.
  • Waiting for Slurm dominates. In cluster mode the dask jobs first wait for the worker jobs to start (about 5 min here), and between rules Snakemake waits for the next jobs to be scheduled, as with local dask. Whole-node worker jobs of more than 3 hours were estimated to start about 22 hours later, so these runs used 96-core jobs of 3 hours or less.
  • It costs more allocation: 46–128 core-hours against 37, since the workers are held for the whole run while mostly idle. --dask_cluster_adaptive (start workers only when there is work) should reduce that; it is not benchmarked here.
  • OME-Zarr outputs can go to MIND instead of local .ozx files (--zarr_store_root auto, below). Results were identical to the matching .ozx runs, with no staging or zip step and no NFS visibility problem (MIND's object store is consistent). But every later step that reads those images now reads them from MIND, which made gmmthresh and region properties 2–5× slower, and runs 2–9 minutes longer. Getting it to work needed fixes for three MIND issues: keys with + or spaces are rejected (422; SPIMquant now uses - in keys), deletes are refused (405; zarr deletes empty chunks), and a dask task reading the token file while the keeper replaced it failed on NFS (a mind_client fix, now retried).
  • In cluster mode, dask performance reports are cluster-wide: a job's report covers everything on the shared scheduler during the job, not just that job.

When the cluster mode should help: compute-bound full-resolution steps (e.g. DoG or instance segmentation, vessel and fibre steps), and many subjects at once, where one node's cores, rather than MIND throughput, are the limit. Those are not tested here; neither is how fast MIND serves many readers at once, which sets the ceiling for everything that reads from it.

How this was measured

  • Local dask (current): default --dask_cluster local. Each dask job requests its usual threads (n4_biasfield and gmmthresh 128, regionprops 64) and starts its own LocalCluster.
  • Cluster: N nodes: --dask_cluster slurm --dask_cluster_jobs 2N --dask_cluster_cores 96 --dask_cluster_mem_gb 340 --dask_cluster_processes 48 --dask_cluster_walltime 3:00:00, i.e. 96 × N workers of 2 threads, about 7 GB each. The dask jobs request 2 cores and 32 GB.
  • Every run started from a copy of the same registration and bias-field outputs. Times come from Snakemake's --benchmark, sacct and the scheduler's metrics log (.dask-cluster/logs/cluster_metrics.tsv). Core-hours are allocated cores × elapsed time of all of the run's Slurm jobs.
  • Queue waits depend on the cluster's load at the time, and each configuration ran once, so totals are only indicative. The per-job times after workers were up are the more reliable comparison.
